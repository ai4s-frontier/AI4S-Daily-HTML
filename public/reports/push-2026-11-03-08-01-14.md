# AI4S前沿观察报告（11.3）

## 📋 总览

- **高原**：科研Agent和形式化工具正在从回答问题扩展到构建模型、生成实验流程并接受机器验证；通用AI的竞争焦点则落到权重编辑、测试闭环与部署成本。
  - **重要新闻事件**：
    - 腾讯混元发布Hyra 2.0，采用Overall–Mission–Worker三层架构管理长期科研任务。
    - 亚马逊用LLM与Lean 4形式化验证Aurora数据分布协议，并发现原文档中的歧义与遗漏假设。
- **高峰**：材料、酶工程与天气预测都出现“模型—实验或观测—验证”的闭环设计，生命科学则同时面对基础模型扩张和AI药物供给增加后的产业消化问题。
  - **重要新闻事件**：
    - 牛津团队用机器学习模拟塑料转化为硬碳的原子级路径。
    - 自动化平台将AI酶设计、无细胞蛋白质合成和性能测试连接起来。
    - 研究提出生成式数据同化方法，并评估AI天气模型集合加入概率预报融合。

## 🌄 "高原"最新洞察

### 科学通用底座

- **科研Agent的产出单位正在变成可复用工具** Hyra 2.0不只自动解题，还展示了HyInv逆折叠模型、HyPLM蛋白质语言模型、覆盖83种元素的HyFF，以及HyProver和HyQEC。Overall–Mission–Worker架构把实验队列、资源审批和独立复核纳入流程，意味着长期科研系统的评价将更多看模型能否留下可复用资产，而非单次答案。

- **科学模型的第一道门槛会变成自动基线与机器验证** 36项科学机器学习任务中，语言模型生成的简单基线中位数恢复了95.5%的性能差距；Amazon则用LLM协助把Aurora协议转成Lean 4并发现文档缺陷。模型负责提出假设、规范和反例，确定性系统负责裁决，这会提高同行评审和工程变更的前置检查密度，也会压缩复杂模型在低增益任务中的空间。

### 通用 AI

- **模型能力的增量开始来自“改对已有能力”** Astra只修改Qwen3.5-0.8B约0.016%的权重，就将MATH-500从7.9%提升到48.1%，但收益主要来自消除32K token循环，并未证明模型获得了新知识。若这一结果能跨模型复现，部署方可能优先采用局部行为编辑；同时，权重写权限和护栏电路保护会成为新的安全边界。

- **Agent产品的竞争会被测试闭环和单位成本牵引** Momentic在60分钟预算中宣称发现约269个缺陷，但每个确认bug成本约2.67美元，高于Codex的0.80美元；其优势依赖设备托管、traces、元素定位、缓存和自动修复。开发者因此会同时追问发现率、误报率和“无法判断”比例，单纯展示Agent完成任务已不足以支撑采购。

## ⛰️ "高峰"最新洞察

### 高能物理与量子科技

- **量子科研Agent必须把搜索和精确验证拆开** Hyra 2.0中的HyQEC覆盖qLDPC量子纠错码构造、码距搜索和精确验证，HyProver则组织猜想、证明与独立复核。对这类高代价任务，语言模型适合扩大候选空间，形式化检查负责淘汰伪解；后续价值取决于可复核的代码、证明和搜索记录，而不是生成结果数量。

### 化学与材料

- **材料AI的验证终点正在从候选分子移到工程原型** A*STAR的MARVEL-AI把材料发现、机器人实验、制造验证连接起来，并披露氢载体复合材料重量降低50%、耐久性提升至4倍且完成全尺寸原型。与此同时，牛津团队用机器学习追踪塑料转化为硬碳的原子级路径。两类工作都把工艺条件和尺度放进评价范围，材料模型若不能进入可重复制备，预测精度很难转化为产品指标。

- **酶设计的瓶颈开始由序列生成转向实验吞吐** 自动化平台将AI候选设计、无细胞表达和性能测试串联，减少人工转接环节。它真正释放的不是更多候选，而是更快获得下一轮训练数据；但当前尚未披露候选数量、成功率或活性提升幅度，因此平台是否能改善单位实验成本仍待验证。

### 生命科学与医学

- **生命科学基础模型正在先解决测量异构性** ProtCell使用约3.8亿个细胞、98个数据集进行预训练，目标是在不同单细胞蛋白质组面板之间建立共享表示。若跨实验室泛化成立，研究团队可用统一表示连接不完整测量，而不必先把所有实验重做一遍；但该成果仍是bioRxiv预印本，独立复现决定其能否成为通用层。

- **AI制药的约束正在从发现能力转向产业消化能力** LifeSciVC文章讨论AI药物发现普及后短期可能出现的药物供给与开发承载压力；这与自动化实验平台的扩张形成对应关系：候选生成和早期验证更快，并不意味着临床、监管和商业化环节同步扩容。药企的筛选重点会因此更看重可验证的差异化和后续开发容量，而不是候选数量。

### 地球科学

- **AI天气模型更可能先成为概率预报组件，而非独立替代者** 生成式数据同化把观测、动力状态和生成模型结合起来，另一项研究则评估将AIFS-CRPS模型集合加入多模型概率融合。AI模型能够低成本生成大量样本，但校准、极端事件和物理一致性仍需融合系统处理；这会使部署重点从单一榜单分数转向跨区域可靠性和尾部风险表现。

- **地球观测中的AI价值取决于把影像识别接到可量化过程** 波罗的海研究利用高分辨率回声测深与AI识别底拖网留下的海床沟痕，火山研究则重新评估热带喷发对全球气候调节的影响。前者说明AI能把大范围观测转成可统计的人类活动信号，后者提醒模型仍需纳入稀有事件和物理机制；二者共同提高了训练数据覆盖与长期观测连续性的要求。

## 📰 今日Top热点

### 1️⃣ [持续跟踪] Hyra 2.0：从自动解题转向自主研发科学工具

* **前情提要**：腾讯混元此前发布Hyra 1.0，采用通用模型驱动的Agent循环解决具有明确评价标准的科研问题。
* **最新进展**：Hyra 2.0将目标扩展到研发可复用的科学模型、研究工作流和软件工具，并以`Overall–Mission–Worker`三层架构管理长期项目、实验队列、资源审批与独立复核。
* **蛋白质与分子模拟**：Hyra 2.0展示了由Agent从头训练的HyInv逆折叠模型和HyPLM蛋白质语言模型；HyInv仅196万参数，官方称其相较ProteinMPNN生成速度提升57倍。HyFF则覆盖83种元素，并用于大规模分子动力学模拟。
* **数学与量子科技**：HyProver用于组织数学猜想、证明和独立复核；HyQEC面向qLDPC量子纠错码，展示了新码构造、码距搜索与精确验证流程。
* **工程工具研发**：系统还参与香山RISC-V处理器的性能优化与形式化验证，并报告发现10个此前未列出的Bug。
* **需要区分**：上述性能、模型对比和科研成果主要来自项目方披露；部分结果仍处于仿真或内部验证阶段，尚不能等同于跨任务、跨实验室的通用能力。
🔗 [Hyra 2.0官方介绍](https://hunyuan.tencent.com/research/hyra2?langVersion=zh) | [Hyra成果仓库](https://github.com/Tencent-Hunyuan/hyra-results/) | [Hyra 1.0](https://hy.tencent.com/research/hyra)

### 2️⃣ AI驱动自动化平台优化酶生产：无细胞合成接入设计闭环

* **核心进展**：研究团队构建自动化平台，将AI酶设计与无细胞蛋白质合成结合，用于筛选和优化工业酶。
* **实验链路**：系统把候选设计、无细胞表达和性能测试连接起来，减少传统酶工程中“设计—合成—检测”之间的手工转换。
* **应用范围**：相关酶可用于原料药、特种化学品、化妆品和食品生产，目标是在更温和的反应条件下提高效率并降低能耗。
* **AI4S意义**：这类系统的价值不只在于生成更多序列，而在于能否将模型候选快速送入实验，并用实验结果反向改进下一轮设计。
* **结果边界**：当前素材没有披露候选数量、实验成功率、活性提升幅度或与现有酶设计方法的系统对比，尚不足以判断平台的实际增益。
🔗 [Phys.org报道](https://phys.org/news/2026-11-automated-platform-optimizes-enzyme-production.html)

### 3️⃣ ProtCell：以3.8亿细胞数据训练单细胞蛋白质组学基础模型

* **模型发布**：研究团队提出ProtCell，使用约3.8亿个细胞、98个数据集进行预训练与评估。
* **训练方式**：模型采用掩码蛋白丰度重建任务，同时学习蛋白质身份和连续丰度信息，形成细胞级与蛋白质级表示。
* **解决的问题**：不同单细胞蛋白质组实验往往检测不完全相同的蛋白面板，导致数据难以直接比较；ProtCell试图在异构面板之间建立共享表示。
* **潜在用途**：模型可用于细胞状态分析、跨实验数据连接，以及设计能够保留更多全蛋白组信息的紧凑测量面板。
* **科研价值**：相比只做分类或单一任务预测，ProtCell更接近为单细胞蛋白组学提供通用表示层。
* **验证边界**：论文目前为bioRxiv预印本，模型性能和跨实验室泛化能力仍需独立复现。
🔗 [ProtCell论文](https://www.biorxiv.org/content/10.64898/2026.10.22.760932v1.full)

### 4️⃣ A*STAR启动MARVEL-AI：把材料发现连接到产业部署

* **项目启动**：新加坡A*STAR牵头启动MARVEL-AI，联合材料发现、自动化实验、制造验证和产业转化环节。
* **示范成果**：项目展示了一种用于氢载体的复合材料胶囊，官方称其重量降低50%、耐久性提升至原来的4倍，并完成从初步发现到全尺寸原型验证。
* **技术路线**：平台面向半导体、能源和先进制造等场景，将AI候选生成与机器人实验、性能验证和工程放大连接起来。
* **AI4S意义**：材料AI的关键评价不止是预测出多少候选，而是候选能否进入可重复实验、工艺验证和真实产品流程。
* **产业化观察**：该项目把“发现—验证—部署”作为连续链路设计，回应了材料模型从实验室指标走向工程性能时的数据与工艺断层。
* **需要区分**：目前披露的复合材料案例和项目目标主要由项目方提供，尚未公布完整实验方案、基线数据和规模化制造结果。
🔗 [A*STAR项目介绍](https://www.a-star.edu.sg/news/press-releases/marvel-ai-accelerating-advanced-materials-innovation-from-discovery-to-deployment)

### 5️⃣ 语言模型自动构建科学基线：36项研究中位数恢复95.5%的性能差距

* **研究问题**：团队考察语言模型能否根据论文上下文，自动为科学机器学习任务构建简单基线，以检查复杂模型是否真正带来增益。
* **评测规模**：研究覆盖Nature、Science及Cell系列期刊中的36个分类和回归任务。
* **主要结果**：自动生成的简单基线平均恢复了从朴素预测器到论文深度学习模型之间差距的85.7%，中位数为95.5%。
* **异常发现**：在12项研究中，自动构建的简单基线达到或超过论文中深度学习模型的表现。
* **AI4S意义**：随着科学机器学习论文数量上升，自动基线可以作为同行评审和研究复核的低成本前置检查，识别数据泄漏、任务设置不合理或复杂模型收益不足等问题。
* **方法边界**：基线质量取决于论文提供的任务描述、数据和实验细节；自动基线不能替代完整复现实验，也不能单独判断论文结论是否错误。
🔗 [arXiv论文](https://arxiv.org/abs/2610.40700)

### 6️⃣ 生成式数据同化用于天气与气候预测

* **论文进展**：研究团队提出生成式数据同化与预测方法，将观测信息、动力系统状态和生成模型结合起来处理天气与气候预测问题。
* **技术重点**：方法面向传统数据同化中观测稀疏、不确定性传播和高维状态估计等问题，尝试通过生成式建模获得更丰富的状态分布。
* **相关进展**：另一项研究评估将AI天气模型集合加入多模型概率预报融合，重点考察校准后的AIFS-CRPS预测与物理模型集合之间的互补性。
* **地球科学意义**：AI模型更适合快速生成大量预测样本，但概率可靠性、极端事件表现和物理一致性仍需通过融合与校准处理。
* **应用边界**：现有素材主要提供方法和评估方向，没有给出足以支持替代传统数值预报系统的长期、跨区域结果。
🔗 [生成式同化论文](https://www.nature.com/articles/s41612-026-01585-4) | [AI天气模型集合论文](https://arxiv.org/html/2610.42130v1)

### 7️⃣ 亚马逊用LLM与Lean 4形式化验证Aurora数据分布协议

* **验证进展**：Amazon Automated Reasoning团队将Aurora数据库的Grover数据修复与迁移协议形式化为Lean 4规范，并证明其在多轮修复和重排过程中保持数据安全。
* **协议属性**：Grover默认采用六副本冗余，目标是容忍六个存储节点中任意两个同时失效；形式化证明不局限于默认副本数量。
* **LLM作用**：LLM协助将自然语言文档转写为Lean规范，并针对每版规范寻找证明或反例；研究人员据此发现原文档中的歧义、遗漏假设和可能导致数据丢失的表述。
* **科学通用底座意义**：该案例把生成式模型用于“提出形式化描述和反例”，再由形式化证明系统负责最终验证，形成模型搜索与确定性检查的分工。
* **工程价值**：团队还证明了机器可验证的显式协议与面向专家的紧凑协议等价，为后续维护和修改提供了可检查的参考实现。
🔗 [Amazon Science官方文章](https://www.amazon.science/blog/proving-the-robustness-of-aws-auroras-data-distribution-protocol-in-lean4)

### 8️⃣ Google与Meta开源TorchTPU，为Google TPU提供原生PyTorch后端

* **开源进展**：Google与Meta合作推出TorchTPU，为Google TPU提供原生PyTorch后端。
* **开发能力**：项目支持动态图执行、编译执行、分布式计算以及面向TPU硬件的优化，目标是减少PyTorch工作负载迁移到TPU时的代码改动。
* **AI4S关联**：科学计算和AI4S研究大量依赖PyTorch生态；原生后端可以降低模型、模拟器和实验代码迁移到专用加速器的工程成本。
* **基础设施意义**：Google TPU若能更顺畅接入PyTorch，将扩大科研团队可使用的硬件选择，也可能促进模型训练、科学模拟和推理工作负载在不同加速器之间流动。
* **当前边界**：素材没有提供与现有PyTorch/XLA路径的独立性能对比，也未说明具体科学模型的迁移结果。

### Astra can read and write weights to improve Qwen

1705 pts · 550 comments · [rikiyat.github.io](https://rikiyat.github.io/blog/weight-space-programming/)

**📌 内容总结**

- 作者想验证：通用前沿 LLM 是否能直接理解、修改甚至从零编写神经网络权重，而不依赖梯度下降、训练循环或专用权重分析模型。
- 关键实验：
  - Astra 仅查看 1.7 万至 2.4 万个权重，就能识别小型 PPO 策略对应的游戏、扩散模型生成的形状，并从 Transformer 中间层识别训练语料和 induction heads。
  - 它修改一个失败的 Kinetix 控制策略，使汽车在 1024 次测试中全部成功，只改动 3.5% 的权重。
  - 它为 MinAtar 的 Breakout、Seaquest、Asterix 从零生成策略权重；Breakout 得分 517.4，高于 PPO 训练 500M 步的 25.3。
  - 在 Qwen3.5-0.8B 上，Astra 用 50 次批量前向评估定位出导致重复思考的方向，修改 131,072 个权重，占模型的 0.016%；MATH-500 从 7.9% 升到 48.1%，GSM8K 从 13.8% 升到 67.1%，IFEval 从 21.0% 升到 62.3%。
- 限制也很明确：Gemma 3 270M 没有明显循环问题时，直接改权重几乎不能增加其数学能力；这更像是移除现有能力的阻碍，而不是凭空增加模型没有的知识或推理能力。大模型实验还依赖 Python 权重操作、有限前向评估和精心设计的 harness。

**💬 讨论总结**

- HN 最认可的是“权重空间可被自然语言模型直接操作”这一能力本身，尤其是从零生成小型游戏策略，以及对 Qwen 只改一个行为方向就显著减少循环。
- 较稳妥的工程解释是：Astra 可能综合了线性代数、神经网络电路、mechanistic interpretability 和大量 ML 经验，并非专门学会了“读权重”这一单一技能。小网络中的输入/输出结构也确实让部分任务可通过权重几何关系推断。
- 讨论中反复强调实验的能力边界：
  - 当前是一个更大的前沿模型优化一个小得多的模型；没有证据表明 Astra 能用同样方法改进自己或同等规模模型。
  - MinAtar 等任务规则简单，模型可能把环境描述直接翻译成手工策略；Qwen 案例的重要性高于 Atari 式的一次性策略生成。
  - Qwen 的主要收益来自消除 32K token 循环，使模型完成原本可能已经具备的答案，并不等同于获得新的数学知识。
- 一些评论担心训练数据泄漏或能力记忆：Astra 可能见过类似模型、权重、电路论文，甚至更大 Qwen 模型的行为。不过这不能完全解释它在具体权重上的定位和编辑效果，仍需跨架构、未见任务和独立模型复现。
- 解释性方面，实验提供了一个实用方向：让强模型协助发现行为对应的权重方向、修改局部电路，类似将 abliteration、行为编辑和 mechanistic interpretability 自动化。但“能修改出有效行为”不等于它已经可靠理解了整个模型。
- 安全讨论集中在权重访问权限：如果模型可以修改其他模型的拒答方向、护栏或行为电路，风险会比传统自蒸馏更直接。不过现实系统通常不会把自身权重或写权限暴露给模型，且当前实验尚未展示递归自我改进。

### Launch HN: Momentic (YC W24) – Agents that catch bugs by using your app

111 pts · 73 comments · [momentic.ai](https://momentic.ai/)

**📌 内容总结**

- 作者想做一个面向工程团队和 coding agents 的 AI QA 平台：让 agent 直接操作 Web、iOS、Android 应用，探索用户流程、发现真实缺陷，并把复现步骤、录屏、截图和 traces 交给开发者。
- 产品分为两类：
  - **Mo**：从自然语言目标出发进行非确定性的探索式测试，重点优化在固定时间内发现更多真实 bug。
  - **回归测试平台**：使用仓库中的 YAML 测试和断言，通过缓存、定位恢复和自动修复维持 CI 中的端到端测试。
- 技术实现包括托管浏览器和移动模拟器、CLI、CI 集成、MCP server、产品知识库、app graph、AI triage 和 reviewed auto-healing。测试结果可回写代码仓库，但默认使用 Momentic 的自然语言格式。
- 公司发布的 QA Bench 覆盖 Gitea、Metabase、Twenty、Saleor 等应用的 1,396 个已标注 bug。在 60 分钟测试预算下，Mo 宣称发现约 269 个 bug，下一名 agent 约 86 个；Mo 的精度约 84%，Codex 约 86%，但 Mo 每个确认 bug 的成本约 2.67 美元，高于 Codex 的 0.80 美元。

**💬 讨论总结**

- 主要认可点是反馈速度和覆盖方式：相比发布后才做人工 UAT，Mo 可以针对每个 PR 的预览环境运行探索测试；对视觉布局、移动端生命周期、异步订阅、AI 输出等传统静态检查难覆盖的问题更有价值。
- 讨论焦点集中在“专用 harness 是否构成长期优势”：
  - 质疑者认为前沿模型升级后可能直接完成相同的 Playwright 操作，团队也可以用 Claude/Codex 加自建 harness 实现类似流程。
  - 公司回应称优势来自两年的测试基础设施、真实应用 traces、元素 grounding、视觉理解、缓存、并行浏览器和领域知识，而不是单个模型调用；但评论普遍认为这仍需持续证明。
- BYOA、可迁移性和锁定是最具体的商业问题。当前 Mo 依赖定制 agent 和自有模型配置，不默认支持用户已有的 frontier model 额度；回归测试的自然语言 YAML 虽然可读，但执行格式和平台能力仍是专有的。用户希望能自带模型、导出 Playwright 或自托管。
- 工程可靠性上，Mo 的探索测试本身是非确定性的；回归测试则通过已解析步骤缓存和恢复机制提高稳定性。评论指出，QA 不仅要统计“找到多少 bug”，还要测量 broken flow 被错误判定为通过的比例，并保留“无法判断”而不是强行给出通过结论。
- 该基准采用 MIT 许可并接受其他 agent，且要求公开、可复现，这有助于缓解厂商自测数据的疑虑；但评论仍追问 1,396 个 bug 中有多少由 Mo 找到，以及无法复现的发现是否会被丢弃。
- 现实限制包括托管设备版本滞后、移动端兼容性、首次配置复杂、结果界面状态不一致、严重级别不可自定义，以及 Slack 授权提示不够清晰。公司称真实设备支持正在开发。

### LongCat-2.5: Native Multimodality for Agentic Tasks

75 pts · 21 comments · [longcat.ai](https://longcat.ai/blog/longcat-2.5/)

**📌 内容总结**

- 作者发布 LongCat-2.5，定位为支持 agentic tasks 的原生多模态模型；但原文页面实际只提供了非常简短的产品入口，缺少模型架构、训练数据、开放权重状态和完整评测方法。
- 社区能确认的信息主要来自评论和外部入口：API 价格据称接近 DeepSeek 4.1F，模型支持约百万 token 上下文；一次测试中有人观察到约 200k token 在 5 分钟内完成，但另一次速度约为 80 tokens/s，性能可能受服务状态影响。
- 页面提供 GitHub、Hugging Face 和聊天入口，但评论者称下载内容和开放权重承诺不清晰，聊天入口曾重定向到异常的 MyKeeta 登录页。

**💬 讨论总结**

- 最大争议不是模型能力，而是发布质量：官方缺少可验证的技术说明、权重获取方式、版本信息和清晰的 benchmark 细节，导致用户无法判断这是开放模型、API 产品还是仅限预览的服务。
- 评测选择也受到质疑。文章将 LongCat-2.5 与较旧的 GPT、Claude 版本比较，却没有说明为何不使用当前版本；支持者认为这可以表示“本地模型追上前沿模型过去几个月的水平”，但这不能替代与当前模型的直接比较。
- 实际试用反馈明显弱于图表印象：有人称 OpenCode 预览版可以完成简单编码任务，但聊天页面出现 Firefox 输入光标问题、重复大量网页搜索、语言和响应行为异常等故障。因此，HN 对 benchmark 与真实 agent 使用体验之间存在较大落差保持谨慎。
- 成本和速度是少数较积极的讨论点：如果 API 价格、上下文长度和吞吐量属实，它可能在特定 agent 场景具备竞争力；但在本地运行场景，评论者认为参数量更大的 LongCat-2.5 未必优于参数更小、活跃参数更少的替代模型。
- 目前缺少足够资料判断其多模态能力、开放权重可用性、推理成本和长期稳定性；链接失效、图表颜色错误和演示站故障也削弱了发布可信度。
